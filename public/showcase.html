분석 파이프라인은 어떻게 동작하나

계약서 사진 한 장이 결과 화면이 되기까지, 누가 누구에게 어떤 JSON을 보내고, 서버는 무엇을 계산하고, 법령 DB는 언제 어떻게 쓰이는지를 실제 코드(2026-11-18 dev 기준)대로 정리했습니다.

1. 구성도2. 시간 순서3. 주고받는 JSON4. 서버 계산5. 법령 DB6. 시간·비용

1. 구성도: 누가 있고 무엇이 오가나

번호는 한 번의 분석에서 일어나는 순서입니다. 법제처 API 점선은 분석 중에는 쓰지 않고, 미리 법령을 채울 때만 씁니다.

번호무엇이 오가나
1앱 → 서버 분석 요청. 서버는 기록만 만들고 바로 202 + analysisId
2저장소 → 서버 서버가 DB의 image_key로 가린 사진을 꺼냄 (요청에는 사진이 없음)
3서버 ↔ GPT 1차(사진 포함), 2차(글만), 필요하면 추가 조회 1회. 모두 JSON 스키마로 답을 받음
4서버 ↔ DB 단계마다 결과 저장, 근거 찾기 때 법령 테이블 검색 (외부 API 호출 없음)
5서버 → 앱 결과 조회 응답. 진행 중이면 진행 단계, 끝나면 결과 전체

2. 시간 순서: 실제 연봉계약서 한 건 (약 80초)

앱은 1번 요청 직후부터 결과를 조회합니다. 진행 중에는 progressStep이 READING_TEXT(1차) → FINDING_TERMS(합치기·규칙) → MATCHING_LAWS(근거) → SUMMARIZING(2차) → DONE으로 바뀌어 진행 화면을 그릴 수 있습니다.

4. 서버가 직접 계산하는 것

AI가 틀리기 쉬운 계산과 확인은 코드가 합니다. GPT는 숫자를 "읽어" 주기만 합니다.

최저임금 (MinimumWageRule)

  1. 월급 기준 금액: valueJson.basePay가 있으면 그것(기본급 + 매월 고정 수당, 연장·야간·휴일 수당 제외), 없으면 amount
  2. 월 시간: 계약서에 적힌 monthlyHours(예: 209)가 있으면 그것. 없으면 계산 
    주 소정시간 = 하루 시간 × 주 일수                 (예: 8 × 5 = 40)
주휴시간   = 주 소정시간이 15시간 이상이면 주 소정시간 × 8 / 40  (예: 8)
월 시간    = (min(주 소정시간, 40) + 주휴시간) × 365 / 84       (예: 48 × 4.345 ≈ 209)
    주 20시간이면 (20 + 4) × 4.345 ≈ 104시간. 하루 시간은 아는데 주 일수를 모르면 계산하지 않고 건너뜀
  3. 시급 = 월급 기준 금액 / 월 시간. 시급제면 그 금액 그대로
  4. 그해 최저임금과 비교. 값은 DB(rule_param)에서 읽음: 2026-01-01부터 10,320원
  5. 미달이면 그 임금 조항을 NEEDS_CHECK(basisType RULE)로 고정하고, 비교 칸(comparison)과 근거 조문(최저임금법 제6조)을 붙임
예: 01 예시 계약서  basePay 2,700,000 / 209시간 = 시급 약 12,918원 ≥ 10,320원  → 통과
예: 시급 10,000원   10,000 < 10,320                                        → "계약서 시급 10,000원 < 2026년 최저임금 10,320원"

빠진 필수 항목 (RequiredItems)

근로기준법 제17조와 시행령 제8조의 6개 항목: 임금, 근로시간, 휴일, 연차휴가, 근무장소, 업무. 주요 조건이 MISSING이면 빠진 항목(analysis_finding)으로 저장합니다.

  • MASKED(사용자가 가림), UNREADABLE(흐림)은 "없다"고 단정할 수 없으니 빠진 항목으로 세지 않음
  • 연봉계약서처럼 임금만 정한 문서(wageOnlyDocument)면 6개를 따로 띄우지 않고 "근로계약서와 함께 확인" 1건으로 안내

그 밖에 코드가 하는 일

계산·확인내용
묶음 합치기5쪽씩 나눠 읽은 결과에서 경계 중복 조항 합치기, 키 다시 매기기
근거 고르기조항당 5개 제한, 같은 조문 중복 제거, L·G 번호 매기기 (아래 5번)
인용 검증준 라벨만, 조문 인용 없으면 UNCERTAIN, 규칙 우선
글 거르기단정 표현("무효", "불법", "위반됩니다", "서명해도 된다" 등), 내부 키, 칸 길이
집계counts.needsCheck = NEEDS_CHECK + UNCERTAIN 수, 우선순위: 규칙 → AI 확인 필요 → 근거 못 찾음, 같으면 쪽·조항 순
일정 후보날짜 이름이 시작·개시·입사면 계약 시작, 종료·만료면 계약 종료, 입주·인도면 입주. 애매한 날짜는 만들지 않음
완료 조건판정 중(JUDGING) 조항이 0개이고 아직 ANALYZING일 때만 COMPLETED (DB 조건부 UPDATE)
알림 문구"{계약서 이름} · 확인 필요 N", 0이면 "{계약서 이름} · 확인할 조항 없음"

5. 법령 DB는 언제, 어떻게 쓰이나

A. 법령 DB를 채우는 때: 분석과 별개, 한 번

  • 서버를 적재 모드로 한 번 실행할 때만 법제처 API를 부릅니다: ./gradlew bootRun --args='--docai.law.load=true'. 평소 서버 기동이나 분석 중에는 법제처 API를 부르지 않습니다.
  • 현행법령 목록(lawSearch.do)으로 법령을 찾고, 본문(lawService.do)을 받아 조·항 단위로 나눠 law_article에 저장합니다. 2026-11-17에 근로기준법, 최저임금법, 근로자퇴직급여 보장법, 주택임대차보호법, 민법 등 7개 법령 2,570행을 넣었습니다.
  • 호출 사이에 간격을 두고, 오류면 1회만 다시 시도합니다. 받은 응답은 파일로 캐시해 두어 다시 적재할 때 API를 또 부르지 않습니다. 인증값(OC)은 로그와 에러 글에서 가립니다.
  • 꼬리표 21개와 조문 연결 110행, 최저임금액(rule_param)은 사람이 확인해서 넣습니다.

B. 분석 중 조회: 근거 찾기 단계에서, 의심 조항마다

  • 의심 표시(issueFound)된 조항만 찾습니다. 의심 없는 조항은 법령을 찾지 않습니다.
  • 기준일은 계약일(law_base_date)입니다. 그날 시행 중인 조문을 고르고, 현행 조문밖에 없으면 내용 앞에 "[현행 조문으로 대신함: 계약일 당시 조문과 다를 수 있음]"을 붙입니다.
  • 전문 검색은 PostgreSQL 전문 검색입니다. 검색어를 글자·숫자만 남겨 질의로 만들고, 점수(ts_rank)가 기준 이상인 조문을 점수 순으로 가져옵니다. 
    SELECT law_article_id, ts_rank(search_vector, to_tsquery('simple', '연장근로 | 가산임금')) AS score
FROM law_article
WHERE search_vector @@ to_tsquery('simple', '연장근로 | 가산임금')
  AND law_id IN (문서 종류의 관련 법령)  AND 기준일에 시행 중
  AND score >= 최소 점수
ORDER BY score DESC  LIMIT 5
  • 조항당 최대 5개. 숫자 규칙이 이미 붙인 근거(RULE)도 칸을 차지합니다. 해석 메모가 있으면 1칸을 남겨 둡니다.
  • 2차의 needMore가 오면 같은 방법(②③)으로 한 번 더 찾아 조항당 최대 3개를 새 라벨로 붙입니다.
  • 찾은 조문은 내용을 복사(ref_text)해 저장하므로, 결과·조항 상세 조회 때는 법령을 다시 찾지 않습니다.
법령 DB에 없는 법령이나 조문은 근거로 쓸 수 없습니다. GPT가 그럴듯한 조문을 지어내도 ②에서 DB에 없으면 버리고, 2차가 준 적 없는 라벨을 인용하면 검증에서 지웁니다. 그래서 화면에 나오는 법령은 모두 우리 DB에 실제로 있는 조문입니다.
